# Contract amendments (v1 → v1.1)

`contracts/contracts.ts` is a copy of `breadcrumb-kit/contracts.ts` (kit left unchanged). Amendments:

1. **`approveRoute(routeId, version, reviewedCheckpointIds)`**. HTTP: `POST /api/routes/:id/approve` with body `{version, reviewedCheckpointIds}`.
   Why: integration.txt requires that "all instructions [are] reviewed", but v1 had no way to express review. The server rejects approval (`409 NOT_APPROVED`) unless every checkpoint id is listed. Each step needs both instructions and a direction or a valid action (amendment 3). The single destination must be last and has no direction or action.
2. **`currentGuidance(sessionId)`**. HTTP: `GET /api/sessions/:id/guidance` → `Result<Guidance | null>`.
   Why: `setLocale` returns a `Session`, which has no guidance text. This re-renders the last accepted decision in the session's current locale. It runs no recognition and allocates no sequence, so changing language cannot move position.
3. **Optional checkpoint actions and manual completion** (lead decision, 2026-10-03). `Checkpoint.action?: CheckpointAction` contains `kind` (`turn`, `door`, `elevator`, `stairs`, `pass_side`, `other`), a literal `target`, nullable `side` (`left`/`right`) and `targetFloor`, ordered bilingual `steps`, and bilingual `completion`. `guiding.direction` is now `Direction | null`. `schemaVersion` stays 1. Missing actions remain missing; legacy routes receive no invented action or evidence.
   Approval requires a non-empty action target, both completion locales and both locales of every ordered step. Elevator actions also require a target floor. Empty step arrays are valid. These checks apply even when an action has a direction.
   Recognition selects an action. Observation evidence must name its target (case-insensitive substring). Repeating its entrance/button view, unknown views or elapsed time never completes it. Only recognizing the next approved checkpoint with its required evidence, or an explicit manual completion, advances. Unconfirmed approach suppresses the arrow. When the next checkpoint has no action, completion requires its recorded identifying evidence.
   `completeAction(sessionId, request)` uses `ManualCompletionRequest` = `{routeVersion, sequence, checkpointId}`. HTTP: `POST /api/sessions/:id/complete-action` with that body. Reserve the sequence through `reserveFrameSequence`. A version mismatch returns `STALE_VERSION`; stale/duplicate sequence returns `STALE_FRAME`; unreserved sequence, unselected/non-action or wrong checkpoint returns `INVALID_INPUT`. The call advances one step and emits only `manual_advance` for the completed checkpoint, never `checkpoint_confirmed`. Evidence explicitly names manual visitor confirmation and says it is not visual proof. The next step is uncertain with no arrow until its approach is observed. A manually reached destination is `arrived` with manual evidence and no visual arrival event.
   `Guidance.text` includes the exact approved instruction, literal target/floor, localized side, ordered steps and completion when guiding an action. The existing speech path reads this text in the session locale. `currentGuidance` re-renders it against the pinned approved version.
4. **Route list** (lead request, 2026-10-04). `listRoutes(): Promise<Result<RouteSummary[]>>` returns one `RouteSummary` per stored route: `id`, `name`, `latestVersion`, `latestStatus`, `approvedVersion` (newest approved version or `null`), `checkpointCount`, `destinationLabel`. Fields come from the latest version. Routes have no timestamps, so none are listed. HTTP: `GET /api/routes`, `no-store`. The route dashboard at `/routes` uses it.

These are not type changes, just conventions:
- **Mock media ids:** `mock:<checkpointId>:approach`, `mock:<checkpointId>:unknown-approach`, `mock:unrelated`, `mock:provider-error` (see `src/shared/mockScenes.ts`). They are valid only in `mode: 'mock'` sessions.
- **Detailed-action fixture:** `contracts/fixture.actions.v1.json` supplies a separate fictional route and named synthetic observations. `src/server/core/actionFixture.ts` resolves them only for that fixture route in mock mode. The unchanged v1 fixture still exercises legacy simple turns. Existing stores are not migrated; the creator's explicit fixture button can add the new draft when absent.
- **`startSession` with a mode that has no recognizer** (currently `live` and `replay`) returns `503 PROVIDER_UNAVAILABLE`. Nothing falls back to mock.
- **Saving a draft** at `version = latest approved + 1` creates the next version. Saving over an approved version returns `409 STALE_VERSION`.
