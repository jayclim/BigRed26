HTTP CONTRACT (PROPOSED)
All JSON endpoints return Result<T>. Success HTTP 200 unless specified below; invalid input 400, not found 404, unapproved/stale state 409, rate limit 429, provider error 503. Error body uses contracts.ts codes. Never leak provider secrets in errors.
POST /api/media: multipart 'file', supported video or JPEG/PNG; returns Result<{mediaId,mimeType}>. Team freezes limits based on actual host/provider support. Return playback URLs only via a controlled media resolver. Browser never uploads provider keys.
POST /api/routes/build: {videoId,name}, HTTP 202 Result<BuildJob>.
GET /api/builds/:id: Result<BuildJob>. UI polls with backoff; no fake processing percentage.
GET /api/routes/:id?version=N: Result<Route>.
PUT /api/routes/:id/draft: Route, Result<Route>. Reject stale version. Publishing creates immutable version snapshot.
POST /api/routes/:id/approve: {version}, Result<Route>. Require all instructions reviewed; preserve provenance.
POST /api/sessions: {routeId,locale,mode}, Result<Session>. Only approved route versions for navigation.
GET /api/sessions/:id: Result<Session>.
PATCH /api/sessions/:id/locale: {locale}, Result<Session>.
POST /api/sessions/:id/frame-sequence: {}, Result<{sequence,routeVersion}>. Atomically reserve a sequence before submitting a frame, including messaging photo frames. Both input adapters use this same allocator.
POST /api/sessions/:id/frame: FrameRequest, Result<Guidance>. Session ID in path must match body.
POST /api/speech: SpeechRequest, Result<SpeechClip>.
GET /api/routes/:id/quality?version=N&since=ISO&mode=live: Result<RouteQuality>.
POST /api/integrations/photon/webhook: provider-specific ingress, signature verification and provider acknowledgement as required by current Photon documentation; normalize into IncomingPhotoHelp internally. Do not pretend the provider sends our internal types.

SESSION AND GUIDANCE RULES
Route versions are immutable once approved. Existing sessions keep their route version; changes apply to new sessions unless the user explicitly restarts.
Only one camera match in flight; drop old queued frames. Client ignores responses with old sequence/version. Both browser and messaging adapters reserve sequence through the core method. Server atomically rejects stale sequences at commit, not only before a model request. A browser frame request and message photo request must be serialized by the same server session mechanism. A browser can reserve again after a stale rejection; it must not guess the next global sequence.
Inspect a short recent frame window and candidates near last confirmed position. Require consistent evidence before changing a turn. Tune on real second-phone footage; 'two consistent frames' is a starting heuristic, not a correctness proof.
App starts at recorded entrance. Match an approach before displaying a camera-relative turn. Location recognition alone does not prove orientation. A reorient state has no arrow.
Unknown view => uncertain, no arrow. Positive evidence of a recognized wrong location can justify off_route; no universal rerouting from unseen corridors. Begin with uncertain as the conservative fallback.
Arrival requires destination evidence. Do not advance on timers. Manual advancing must have visible control and create manual_advance events. Do not present manual advancement as model recognition.
Voice reads only current guidance, cancels queued stale audio, deduplicates by instruction ID, and never blocks the camera UI. Changing locale yields new text/audio for the same route state.
Record events with mode and route version. Metrics default to live only. Replay preserves original event timing but must not inflate live totals. Mock metrics visibly labelled. Session identifiers are pseudonymous; no need to store raw visitor video for analytics.

DESIGN CONTRACT
Warm near-white creator screen; dark camera chrome; vivid cyan as the primary guide accent; amber uncertainty; green arrival. Use one accent consistently. Large instruction text and a compact reference image; four controls at most: sound, language, help, exit.
Three main screens: create/review; follow; arrival. Quality is a secondary organizer view.
Gentle 200–300 ms transitions are an initial design target, respecting reduced motion. Keep arrows stable while requests process. On uncertainty remove the arrow and show a useful action such as 'Point toward the room sign'.
No fake millimeter precision, moving floor arrows, confidence percentages or loading percentages. Avoid dashboard chrome around the visitor camera.
Desktop demo: two generous panes for teach and follow, phone view large enough to read, matched reference shown briefly. Add a third small message view only during the Photon-specific demonstration.

Interface: all contract states work against fixtures; route review editable; permission denied screen; sound toggle; captions; portrait phone layout; keyboard/focus usability for web controls. Include screenshots of each state.
